# Dalnovid — новое ядро (собственный код)

Решение от 2026-10-12: уходим от кода RustDesk полностью — и клиент, и сервер. Причина: часть функций будет бесплатной, часть платной. Платные модули должны быть нашим собственным кодом, а текущий форк под AGPL-3.0 этого не позволяет.

## 1. Правила «чистой комнаты»

Новое ядро — новая работа, а не перевод форка.

1. Новый код живёт в **отдельных репозиториях**. Ни одного файла, функции или `.proto` из форка туда не переносим, даже «временно».
2. Пишем по **собственной спецификации** (этот документ и `docs/protocol.md` в новом репозитории), а не по исходникам RustDesk. Свой протокол, свои форматы сообщений, свои имена.
3. Используем **только зависимости под разрешительными лицензиями**: MIT, Apache-2.0, BSD, ISC, Zlib, MPL-2.0 (MPL — только без изменений файлов библиотеки). GPL, LGPL со статической линковкой, AGPL и все крейты RustDesk запрещены. В CI это проверяет `cargo-deny` и проверка лицензий Flutter-пакетов: сборка падает, если просочилась запрещённая лицензия.
4. Совпадать с RustDesk могут только идеи и общеизвестные подходы (P2P, relay, ID устройства). Они не защищены авторским правом, а код и его структура защищены.
5. Сторонние участники подписывают **CLA**, чтобы права на код были у владельца проекта и его можно было лицензировать по-разному.
6. Перед публичным платным релизом схему лицензирования проверяет юрист по IT-праву.

Форк (`dalnovid-client`, `dalnovid-server`) до выхода нового ядра остаётся рабочим продуктом: в нём только исправления, без новых функций.

## 2. Лицензии нового кода (open core)

| Часть | Лицензия | Почему |
| --- | --- | --- |
| Ядро клиента и базовый сервер | открытый код, лицензию выбираем сами (например, Apache-2.0 или AGPL-3.0 с правом двойного лицензирования у владельца) | доверие: любой может проверить шифрование и собрать сам |
| Платные модули (командная работа, веб-панель, аудит, SSO и т.д.) | проприетарная | то, за что платят |

Владелец всего кода — проект. Поэтому, даже если ядро выйдет под AGPL, мы можем продавать коммерческие лицензии и закрытые модули.

## 3. Бесплатное и платное (черновик, нужно утвердить)

Принцип: **безопасность никогда не платная.** Шифрование, проверка сервера, свой сервер и код сеанса доступны всем — платными бывают масштаб, управление и удобство для команд.

| Бесплатно | Платно (Pro / Business) |
| --- | --- |
| Подключение по ID, просмотр и управление | Общие адресные книги, команды, роли |
| Шифрование всегда, проверка ключа сервера, код сеанса | Веб-панель администратора |
| Свой сервер (один), relay | Журнал аудита и запись сеансов |
| Передача файлов, буфер обмена | Несколько серверов и relay, отказоустойчивость |
| Личная адресная книга с синхронизацией (E2E) | SSO / LDAP / Active Directory |
| Неконтролируемый доступ на своих устройствах (лимит устройств) | Неограниченное число устройств, политики доступа |
| Все платформы | Массовая установка (MSI/GPO, MDM), свой брендинг клиента |
| | Веб-клиент в браузере, приоритетная поддержка |

## 4. Архитектура

```
┌──────────────── Клиент (одно приложение на всех ОС) ────────────────┐
│  Flutter UI (по утверждённым макетам)                               │
│        │ flutter_rust_bridge (MIT)                                  │
│  dalnovid-core (Rust)                                               │
│   ├─ session   — протокол сеанса, роли, подтверждения, код сеанса   │
│   ├─ transport — WebRTC (str0m): ICE/STUN/TURN, DTLS, SRTP, каналы   │
│   ├─ media     — захват экрана → кодер → RTP; декодер → отрисовка   │
│   ├─ input     — мышь, клавиатура, касания, перо                    │
│   ├─ clipboard, files, audio                                        │
│   ├─ identity  — ключи устройства и пользователя, хранилище ОС      │
│   └─ addrbook  — E2E-адресная книга (см. ROADMAP)                   │
│  dalnovid-agent — служба для неконтролируемого доступа              │
│   (Windows service / launchd / systemd), запускает core на хосте    │
└─────────────────────────────────────────────────────────────────────┘
                 │ WebSocket (TLS)                    │ TURN (UDP/TCP/443)
┌──────────────── Сервер (свой, open core) ───────────────────────────┐
│  dalnovid-signal — регистрация устройств, ID, присутствие,          │
│                    обмен SDP/ICE (сам медиаданные не видит)         │
│  dalnovid-api    — учётные записи, адресные книги (только шифр),    │
│                    приглашения, обновления                          │
│  relay           — coturn (BSD) или свой TURN на Rust               │
│  [платно] admin-web, audit, SSO, multi-relay                        │
└─────────────────────────────────────────────────────────────────────┘
```

### Почему WebRTC

- Обход NAT (ICE), relay (TURN), шифрование (DTLS-SRTP) и контроль перегрузки — проверенные стандарты, а не самописные.
- Работает через 443/TCP, когда UDP закрыт, — это закрывает жалобы «не подключается».
- Даёт **веб-клиент в браузере** почти бесплатно — это сильная платная функция.
- Реализация на Rust: `str0m` (MIT/Apache-2.0), sans-IO, без огромной libwebrtc.

### Доверие и шифрование

- У каждого устройства своя пара ключей Ed25519. ID устройства выводится из открытого ключа, поэтому подменить устройство нельзя.
- Отпечатки DTLS обеих сторон подписываются ключами устройств и сверяются в клиенте. Сервер сигнализации не может встать посередине (MITM).
- Код сеанса (короткая строка из общих ключей) показывается на обеих сторонах — тот самый «9D11 · 03FE · A6C2» из макетов.
- Ключ сервера закрепляется при первом подключении (TOFU) или вшивается в сборку.
- Ключи хранятся в хранилище ОС: DPAPI, Keychain, Android Keystore, Secret Service.

### Платформенные части (все под разрешительными лицензиями)

| Задача | Windows | macOS | Linux | Android / iOS |
| --- | --- | --- | --- | --- |
| Захват экрана | DXGI Desktop Duplication (`windows`) | ScreenCaptureKit (`screencapturekit`) | X11: `xcap`; Wayland: PipeWire через портал (`ashpd`) | MediaProjection / ReplayKit (позже) |
| Кодирование | Media Foundation (аппаратно), OpenH264 | VideoToolbox, OpenH264 | VA-API, OpenH264 | MediaCodec / VideoToolbox |
| Ввод | SendInput | CGEvent | XTest; Wayland: libei / RemoteDesktop-портал | Accessibility (позже) |
| Буфер обмена | `arboard` | `arboard` | `arboard` | системные API |
| Служба | Windows Service (`windows-service`) | launchd | systemd | — |

Кодеки по шагам: H.264 (аппаратно + OpenH264, BSD) → VP9 (libvpx, BSD) → AV1 (dav1d / rav1e, BSD).

## 5. План до версии 1.0

Ориентировочно, для одного-двух разработчиков с моей помощью.

| Этап | Срок | Результат |
| --- | --- | --- |
| **M0. Основа** | 2–3 недели | Новые репозитории, CI, проверка лицензий, спецификация протокола, сервер сигнализации, ключи устройств |
| **M1. Первая картинка** | 4–6 недель | Windows → Windows: просмотр экрана через P2P и TURN, H.264, шифрование и код сеанса |
| **M2. Управление** | ~4 недели | Мышь, клавиатура, буфер обмена, окно подтверждения на хосте, macOS как хост и клиент |
| **M3. Приложение** | ~4 недели | Flutter-интерфейс по макетам (светлая и тёмная темы), Linux X11, передача файлов, учётные записи и E2E-адресная книга |
| **M4. Бета 1.0** | 3–4 недели | Служба для неконтролируемого доступа, установщики, подписанные сборки и автообновление, диагностика подключения |
| **После 1.0** | — | Android (хост и клиент), iOS (клиент), Wayland, звук; платные модули: веб-панель, команды, аудит, SSO, веб-клиент |

Итого до беты 1.0 — примерно 4–5 месяцев. До паритета с текущим форком по платформам — около года.
